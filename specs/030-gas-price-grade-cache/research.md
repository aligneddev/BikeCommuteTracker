# Phase 0 Research: Gas Price Grade Selection & Cache Refresh Policy

## Decision 1: EIA product-series facet maps directly to rider grade (`EPMR` / `EPMP`), replacing the all-grades `EPM0`

- **Decision**: `EiaGasPriceLookupService` will select the `facets[product][]` value based on the requested grade: `EPMR` ("Regular Gasoline") for `Grade.Regular`, `EPMP` ("Premium Gasoline") for `Grade.Premium`. The `duoarea=NUS`, `frequency=weekly`, `sort`/`length=1` request shape is unchanged — only the `product` facet value varies by grade. Confirmed live against the EIA Open Data API v2 facet-metadata endpoint (`GET /v2/petroleum/pri/gnd/facet/product`), which returns `EPMR` = "Regular Gasoline" and `EPMP` = "Premium Gasoline" as distinct facets from the currently-used `EPM0` = "Total Gasoline" (the all-grades blend the app has always queried).
- **Rationale**: The spec's Current Behavior section and Assumptions explicitly call out that the existing `EPM0_PTE_NUS_DPG`-style series is an all-grades blend, not a per-grade series, and that "the closest available regular/premium series is used" if a direct equivalent isn't available — `EPMR`/`EPMP` are in fact direct, correctly-named equivalents, so no fallback/approximation is needed.
- **Alternatives considered**: Continuing to use `EPM0` for both grades and only varying a display label (rejected — defeats the entire purpose of the feature per SC-001, which requires the *fetched* price, not just the label, to differ by grade); using regional (`duoarea`) series instead of national (`NUS`) (rejected — out of scope; the existing implementation and spec both scope to the national weekly average, and no `LocationLabel`-to-EIA-region mapping is described anywhere in the spec or existing code).

## Decision 2: `GasPriceLookupEntity.Grade` is a new nullable column; legacy rows are never migrated, so they never match new grade-aware queries

- **Decision**: Add `public string? Grade { get; set; }` to `GasPriceLookupEntity`. The column is nullable at the database level (so the EF Core migration can add it without requiring a default-value backfill for the ~thousands of potential pre-existing rows). Every row written by the *updated* service code always sets `Grade` to a non-null `"Regular"` or `"Premium"` literal. The unique index changes from `HasIndex(x => x.WeekStartDate).IsUnique()` to `HasIndex(x => new { x.WeekStartDate, x.Grade }).IsUnique()`. All read/write paths in the updated service query `WHERE WeekStartDate = @week AND Grade = @grade` with `@grade` always bound to a concrete value — a legacy row (`Grade = NULL`) can never satisfy `Grade = @grade` for any non-null `@grade`, so it is structurally unreachable by any new code path without a special-cased "legacy fallback" branch, which the spec explicitly forbids (FR-004a: legacy rows "MUST NOT be matched by any grade-aware lookup").
- **Rationale**: This is the simplest design that satisfies FR-004a exactly as clarified ("Leave existing rows as-is... they become inert history") with zero migration-time data rewriting, and it reuses the existing "unique index + insert-races-to-conflict-then-reread" concurrency pattern (`DbUpdateException` catch block in `GetOrFetchAsync`) unchanged in shape — just extended to a composite key. SQLite (and EF Core's generated unique index) treats each `NULL` in an indexed column as distinct from every other `NULL`, so multiple legacy rows (all with `Grade = NULL`) do not collide with each other under the new composite unique index, and they don't collide with new graded rows for the same week either (a legacty row's `WeekStartDate` may coincidentally equal a new row's `WeekStartDate`, but `(week, NULL)` and `(week, "Regular")` are different index entries).
- **Alternatives considered**: Backfilling legacy rows with an assumed grade, e.g. `"Premium"` to match FR-002a's UserSettings backfill (rejected — spec edge case explicitly rejects this: "they are left as-is... rather than being migrated, deleted, or backfilled with an assumed grade"); making `Grade` non-nullable with an EF migration default-value backfill to a sentinel like `"Legacy"` (rejected — that sentinel would still need to never match `"Regular"`/`"Premium"` queries, which is exactly what `NULL` already achieves for free, and a sentinel string invites accidental matches/typos where `NULL` cannot).

## Decision 3: Stale-refresh de-duplication via a singleton `GasPriceRefreshCoordinator` (per-key async lock keyed by `(WeekStartDate, Grade)`)

- **Decision**: Introduce `GasPriceRefreshCoordinator`, a thread-safe singleton (registered via `AddSingleton`, since `EiaGasPriceLookupService` itself is `AddScoped` per existing DI registration and cannot hold cross-request state). It exposes `Task<T> RunExclusiveAsync<T>((DateOnly weekStart, string grade) key, Func<Task<T>> refresh)`, implemented with a `ConcurrentDictionary<(DateOnly, string), SemaphoreSlim>` (one 1-count semaphore per in-flight key, removed once no longer needed) so that concurrent stale-refresh attempts for the same `(week, grade)` serialize: the first caller performs the actual EIA HTTP call and cache write; subsequent concurrent callers for the same key await the same semaphore, then re-read the now-fresh (or still-stale-but-attempted) cache row instead of independently calling the external API.
- **Rationale**: FR-007a and SC-003 require at most one external call per `(week, grade)` per staleness event even under concurrency. The existing codebase has no cross-request in-process coordination primitive to reuse (the closest precedent, `SemaphoreSlim` in `ImportJobProcessor`, is a *rate-limiting* throttle across many different keys within one batch job, not a per-key mutual-exclusion/de-duplication lock across independent HTTP requests) — a small dedicated singleton is the least-complex fit, consistent with the "local-first, single API instance" runtime posture (Constitution Directive 8), where an in-process lock is sufficient (no distributed lock/Redis needed).
- **Alternatives considered**: Relying solely on the existing "insert races to unique constraint, re-read on conflict" DB-level pattern for de-duplication too (rejected — that pattern only prevents duplicate *writes*, not duplicate *external HTTP calls*; two concurrent requests would still each independently call the EIA API before either write happens, violating "no more than one external gas price lookup... within any 3-day window" per SC-003); a database-level advisory lock/`SELECT ... FOR UPDATE` (rejected — SQLite has no row-level locking primitive equivalent, and the local-first single-instance deployment makes an in-process lock sufficient); a distributed cache/lock service (rejected — massive over-engineering for a local-first SQLite app with one API process).

## Decision 4: Freshness/"now" comes from the already-registered `TimeProvider`, not `DateTime.UtcNow`

- **Decision**: `EiaGasPriceLookupService` will accept `TimeProvider` via constructor injection (already registered as `TimeProvider.System` in `Program.cs` per repo convention) and compute staleness as `timeProvider.GetUtcNow().UtcDateTime - cached.RetrievedAtUtc >= TimeSpan.FromDays(3)`, replacing the current direct `DateTime.UtcNow` write-timestamp call (which remains for *writing* `RetrievedAtUtc`, now also sourced from `TimeProvider`).
- **Rationale**: `docs/agent/testing-and-quality-gates.md` states: "Inject `TimeProvider`... into any service that needs 'now'/'today' instead of calling `DateTime.Now`/`DateTime.UtcNow` directly," specifically so calendar/boundary logic doesn't depend on wall-clock time in tests. The 3-day staleness boundary is exactly this kind of time-boundary logic (Acceptance Scenario 4 in US2 requires the window to "survive restarts" and be measured purely from the durable timestamp — a fake/controllable clock is essential for deterministic tests of "just under 3 days" vs. "3+ days").
- **Alternatives considered**: Keeping `DateTime.UtcNow` (rejected — violates the documented convention and makes the 3-day-boundary tests flaky/dependent on real wall-clock timing, exactly the problem `TimeProvider` was adopted to solve elsewhere in the codebase, e.g. `TestSupport.FakeTimeProvider` usage for weekly/monthly boundary tests).

## Decision 5: Grade/freshness/de-duplication logic lives entirely in the C# `Application/Rides` layer; the F# domain project is untouched

- **Decision**: No changes are made to `BikeTracking.Domain.FSharp`. Grade selection (which EIA series to call), cache-key composition, staleness comparison, and refresh de-duplication are all I/O-adjacent orchestration concerns (HTTP calls, EF Core reads/writes, an in-process lock) rather than pure business calculations, so they stay in the existing C# application-service layer, consistent with how the *existing* `GasPriceLookupService.cs` (and its sibling `WeatherLookupService`) are already implemented entirely in C# with no F# involvement.
- **Rationale**: The constitution's Result-style/pure-domain-calculation directive (Directive 6) applies to *domain business rules* (e.g., `AdvancedDashboardCalculations.fs`'s pure savings math) — grade/cache/HTTP orchestration is not a business calculation with multiple pure branches to unit-test in isolation; it is inherently stateful (DB reads/writes, HTTP, a lock). Introducing an F# module here would not simplify testing (the existing `GasPriceLookupServiceTests.cs` already tests this orchestration directly and effectively with the SQLite in-memory provider + stub `HttpMessageHandler`) and would add an unnecessary cross-language boundary.
- **Alternatives considered**: Extracting a pure F# `resolveGasGradeSeries : Grade -> string` mapping function (rejected — a single 2-branch string mapping does not justify a cross-project/cross-language call for no testability benefit; it is trivially covered by C# unit tests on the service itself).

## Decision 6: `UserSettings.GasGrade` stored as a `string` with two allowed literal values, mirroring existing enum-like string columns

- **Decision**: Add `public string GasGrade { get; set; } = "Regular";` to `UserSettingsEntity` (non-nullable, default `"Regular"` at the CLR level for newly-constructed instances before a row is saved — matching FR-002). The EF Core migration adds the column as non-nullable with a SQL-level default/backfill of `'Premium'` applied to all pre-existing rows in the same migration (via `migrationBuilder.Sql(...)` or `UpdateData`), then the column keeps `"Regular"` as the default for any row inserted after the migration runs (satisfying FR-002 vs. FR-002a's differing defaults for new-vs-existing rows). Allowed values are validated at the service layer (`UserSettingsService`) against a small `{"Regular", "Premium"}` set, consistent with how other string fields in this codebase (e.g. `DataSource`, `PrecipitationType`) are free-text-but-conventionally-constrained rather than backed by a DB enum type (SQLite has no native enum type).
- **Rationale**: Matches the existing precedent of representing small closed sets as validated strings rather than introducing a new EF Core enum conversion or a lookup table, keeping the change minimal and consistent with `DataSource`/`GasPriceResponse.DataSource`-style string fields already in this codebase. A CHECK constraint (matching the existing `CK_UserSettings_*` pattern already used for numeric ranges) is added to enforce `GasGrade IN ('Regular', 'Premium')` at the database level too.
- **Alternatives considered**: A C# `enum GasGrade { Regular, Premium }` persisted as an int (rejected — every other comparable field in `UserSettingsEntity`/`GasPriceLookupEntity` that represents a closed string-like set, e.g. `DataSource`, uses `string`, and an int enum would be less self-describing in raw SQLite inspection/debugging, which this local-first app relies on); a separate `GasGrades` lookup table (rejected — massive over-engineering for a 2-value constant set).
