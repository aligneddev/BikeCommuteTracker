# Research: Monthly Summary Import

**Feature**: `025-monthly-summary-import` | **Phase**: 0 | **Date**: 2026-06-25

All unknowns from the Technical Context have been resolved by examining the existing codebase. No external research queries were needed — all decisions derive directly from existing code patterns.

---

## Finding 1: Import Infrastructure Reusability

**Decision**: Reuse `ImportJobEntity`, `ImportRowEntity`, and `ImportJobProcessor` unchanged.

**Rationale**: The existing import infrastructure is generic. `ImportJobProcessor` iterates pending `ImportRowEntity` rows and calls `RecordRideService.ExecuteAsync` for each one. It does not know or care how rows were generated — whether from a CSV parser or a monthly summary expansion. Monthly-generated rides simply become `ImportRowEntity` rows populated at preview time. Progress tracking, realtime notifications, cancellation, and duplicate resolution all work for free.

**Alternatives considered**:
- *New standalone import pipeline*: Rejected — duplicates progress tracking, cancellation, and SignalR notification logic already proven in CSV import.
- *Process monthly rides synchronously without job infrastructure*: Rejected — FR-013 requires an import summary panel identical to per-ride CSV import; the job model is the right abstraction.

---

## Finding 2: Weekday Distribution Algorithm Placement

**Decision**: New F# module `MonthlySummaryDistributor.fs` in `BikeTracking.Domain.FSharp`.

**Rationale**: The distribution algorithm is a pure function with no I/O — given (month, year, totalMiles, days), it deterministically returns a list of (date, miles) pairs. This is the same kind of computation as existing F# domain modules (`WindResistance.fs`, `AdvancedDashboardCalculations.fs`). F# is the designated home for pure domain logic per the architecture principles.

**Algorithm**:
```
weekdays = all Mon–Fri in (month, year), sorted ascending
weekday_count = weekdays.Length
if days > weekday_count → Error "Days (N) exceeds available weekdays (M) in {month} {year}"
stride = max(1, weekday_count / days)   // integer division
selected = [weekdays.[i * stride - 1] for i in 1..days]   // 1-indexed, stride-spaced
per_day = floor(totalMiles / days * 100) / 100             // 2 dp truncation
remainder = totalMiles - per_day * days
rides = selected[0..days-2] with per_day miles, selected[days-1] with per_day + remainder
```

**Alternatives considered**:
- *C# implementation*: Would work, but places computation logic in Application layer, not domain. F# provides exhaustive pattern matching and immutable data that reduces defensive null checks.
- *Front-load weekdays (pick first N)*: Rejected — spec requires even spread (stride-based selection).

## Finding 3: Source Tag on Ride Records

**Decision**: Add `ImportSource string?` nullable column to `RideEntity` and `RecordRideRequest`.

**Rationale**: `RideEntity` currently has no source discriminator. The spec requires a `monthly-import` tag to distinguish generated rides from manual entries and CSV imports. Adding a dedicated column is cleaner than overloading `Notes` or a future tags field. It enables unambiguous filtering and reporting.

**Values**:
- `NULL` — manually recorded ride (no change to existing RecordRideService flow)
- `"csv-import"` — (optional, future) retroactive tag for CSV-imported rides
- `"monthly-import"` — rides generated by monthly summary import

**Migration strategy**: `ALTER TABLE Rides ADD COLUMN ImportSource TEXT NULL` — additive, non-breaking. Existing rows remain `NULL`.

**Alternatives considered**:
- *Store in Notes field*: Rejected — pollutes user-visible notes; not queryable without LIKE.
- *Separate `RideSourceTag` table*: Overkill for a single nullable string.

## Finding 4: Import Type Discriminator on Jobs

**Decision**: Add `ImportType TEXT NOT NULL DEFAULT 'csv'` to `ImportJobEntity`.

**Rationale**: The audit log (FR-015) should only be written for monthly-summary import jobs. The `ImportJobProcessor` needs to know the job type to conditionally write the audit log. A string discriminator column on the job is the simplest approach, consistent with existing `Status` string patterns.

**Values**: `"csv"` (existing default), `"monthly-summary"` (new).

**Migration**: Additive — `DEFAULT 'csv'` ensures all existing jobs are correctly typed.

---

## Finding 5: Audit Log Strategy

**Decision**: New `MonthlySummaryAuditLogs` table, written atomically at job completion.

**Rationale**: FR-015 requires an immutable, timestamped record of every completed import. A separate table is queryable and decoupled from the mutable job status table. Written in the same `SaveChangesAsync` transaction as the `Status = "completed"` update to guarantee atomicity. No UPDATE or DELETE operations are ever performed on this table — enforced by the entity having no setters after construction.

**Alternatives considered**:
- *Append to `LastError` JSON*: Too lossy; loses individual field granularity.
- *Event outbox*: Unnecessary overhead; audit log is local-only.

## Finding 6: New API Endpoint Group

**Decision**: `/api/monthly-imports` route group (new `MonthlyImportEndpoints.cs`), separate from `/api/imports`.

**Rationale**: The preview input shape differs significantly (monthly text/file + year vs. CSV file only). A separate endpoint group avoids adding a `type` switch to the existing import endpoints and keeps the per-ride CSV import and monthly summary import as independent, replaceable adapters.

**Contracts reused**: `ImportStartRequest`, `ImportStatusResponse`, `ImportCancelResponse` — identical semantics.
**New contracts**: `MonthlyImportPreviewRequest`, `MonthlyImportPreviewResponse`, `MonthlyImportPreviewRow`, `MonthlyImportMonthRow`.

## Finding 7: Year Assignment Logic

**Decision**: Year assignment in `MonthlySummaryImportService`, not in the F# domain.

**Rationale**: Year assignment requires knowledge of the input *sequence* (to detect a Dec→Jan boundary), which is an orchestration concern, not a pure domain invariant. The rule is: assign `StartYear` to all months until a January follows a non-January; subsequent months get `StartYear + 1`. This is simple enough for C# application logic.

**Algorithm**:
```
year = startYear
previousMonth = null
for each parsed row (ordered by input position):
    if previousMonth is not null and parsedMonth < previousMonth:
        year += 1   // crossed year boundary (e.g., Dec=12 → Jan=1)
    row.Year = year
    previousMonth = parsedMonth
```

## Finding 8: Intra-File Duplicate Month Detection

**Decision**: Backend validation in `MonthlySummaryValidationRules`, flagged as `DUPLICATE_MONTH` error on all affected rows.

**Rationale**: If the same month appears twice in the pasted data, both rows must be flagged — the rider must resolve by removing one before confirming. This is a validation concern, not a business rule, so it lives in `MonthlySummaryValidationRules`. Because intra-file duplicate detection requires cross-row awareness, it runs as a second pass after per-row validation.

---

## Finding 9: Header Detection and Warning

**Decision**: If no recognisable header row is detected (no row containing case-insensitive "month" and ("miles" or "days")), the system falls back to positional column order (Month=col0, Miles=col1, Days=col2) and sets `HeaderDetectionWarning = true` in the preview response.

**Rationale**: FR-003 requires this. The warning is displayed as a banner in the UI requiring the rider to confirm column mapping before proceeding to confirmation.

**Implementation**: `MonthlySummaryParser` checks the first row. If it fails header detection, treat first row as data (not skipped) and set flag. Frontend disables "Confirm Import" until rider explicitly dismisses the column-mapping warning.

---

## Finding 10: RecordRideService Miles Validation

**Decision**: Monthly rides bypass the 200-mile per-ride cap that exists in `RecordRideService.ExecuteAsync`.

**Rationale**: Per-day miles from monthly distribution will typically be well under 200. However, the spec says riders can input any positive miles total. If `floor(totalMiles / days)` exceeds 200, `RecordRideService` will throw. Given the domain rule is "miles per ride ≤ 200", the validation in `MonthlySummaryValidationRules` should check that `per_day_miles ≤ 200` and flag the row as invalid if not. This keeps domain rules consistent and prevents a runtime exception in the processor.

**Added validation rule (not in original spec)**: If computed per-day miles > 200, flag row with `MILES_PER_DAY_EXCEEDS_LIMIT`.
