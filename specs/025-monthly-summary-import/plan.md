# Implementation Plan: Monthly Summary Import (Auto-Split to Daily Rides)

**Branch**: `025-monthly-summary-import` | **Date**: 2026-06-25 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/025-monthly-summary-import/spec.md`

## Summary

Rider pastes or uploads a Month/Miles/Days table. The system parses the input, lets the rider select a year, then distributes each month's total miles evenly across `Days` weekdays in that calendar month — producing individual `Ride` records, one per day. The flow reuses the existing import job infrastructure (job entity, row entity, processor, duplicate resolution, progress tracking) while adding a new API endpoint group, a new F# domain module for weekday distribution, two schema migrations, and a new React frontend page.

## Technical Context

**Language/Version**: .NET 10 (C# 13 backend), F# 9 (domain layer), TypeScript 5.x (React 19 frontend)

**Primary Dependencies**: ASP.NET Core Minimal API, Entity Framework Core 9 (SQLite), xUnit + Moq (backend tests), Vitest + React Testing Library (frontend unit), Playwright (E2E)

**Storage**: SQLite via EF Core Code-First migrations, auto-applied on startup. Three schema changes required: `ImportSource` on `RideEntity`, `ImportType` on `ImportJobEntity`, new `MonthlySummaryAuditLogs` table.

**Testing**: `dotnet test BikeTracking.slnx` (backend + domain), `npm run test:unit` in `src/BikeTracking.Frontend`, `npm run test:e2e` for E2E gate.

**Target Platform**: Local-first desktop (SQLite, .NET Aspire, Tauri sidecar). No cloud dependency.

**Project Type**: Web-service with React frontend (existing app extension).

**Performance Goals**: Synchronous import, ≤ 12 months, ≤ ~260 generated rides — completes in milliseconds. No performance gate beyond interactive responsiveness.

**Constraints**: Max file upload 5 MB (existing limit). Weekdays = Mon–Fri, no public holiday exclusions. English month names only (full names + 3-letter abbreviations).

**Scale/Scope**: Single-rider per session. Import generates at most ~260 rides (52 weeks × 5 days). No pagination or async background concern beyond existing `ImportJobProcessor` pattern.

## Implementation Phases

### Phase 1 — Domain: Weekday Distribution (F#)

**Scope**: New pure F# module `MonthlySummaryDistributor.fs`.

**Functions**:
- `getWeekdays (month: int) (year: int) : DateOnly list` — returns all Mon–Fri dates in the given calendar month, sorted ascending
- `selectWeekdays (weekdays: DateOnly list) (days: int) : Result<DateOnly list, string>` — applies stride selection: `stride = max(1, floor(count / days))`, first selected = `weekdays.[stride - 1]`; returns error if `days > count` or `days < 1`
- `distributeRides (month: int) (year: int) (totalMiles: decimal) (days: int) : Result<(DateOnly * decimal) list, string>` — composes above; per-day miles = `floor(totalMiles / days * 100M) / 100M`; remainder added to last ride

**TDD gate**: Unit tests in F# or C# test project covering stride selection, rounding remainder, boundary cases (days=1, days=weekdayCount, days>weekdayCount).

### Phase 2 — Backend: Schema Migrations

**Scope**: Three EF Core migrations.

1. **AddImportSourceToRides** — adds `TEXT NULL ImportSource` to `Rides` table; default `NULL` (manual rides have no source). Migration test: verify column exists and existing rows have `NULL`.
2. **AddImportTypeToImportJobs** — adds `TEXT NOT NULL ImportType DEFAULT 'csv'` to `ImportJobs` table. Migration test: verify existing rows read as `'csv'`.
3. **AddMonthlySummaryAuditLogs** — creates `MonthlySummaryAuditLogs` table (see data-model.md for schema). Migration test: verify table exists with all columns.

Also extend:
- `RecordRideService.ExecuteAsync` to accept and persist `ImportSource` from `RecordRideRequest`
- `RecordRideRequest` contract: add optional `ImportSource string?` parameter
- `ImportRowEntity`: add `ImportSource string?` column (same migration as rides, or separate)
- `ImportJobProcessor.BuildRecordRideRequest`: pass `row.ImportSource` through

### Phase 3 — Backend: New Import Service + Endpoints

**Scope**: Parser, validation, service, contracts, endpoints.

`MonthlySummaryParser.cs`:
- Accepts raw text string
- Detects delimiter (tab preferred, then whitespace)
- Case-insensitive header matching (Month, Miles, Days)
- No-header fallback: positional columns with `HeaderDetectionWarning = true` flag in result
- Month name normalisation: full English names + 3-letter ISO abbreviations → `int month`
- Miles: strip commas, parse decimal
- Days: parse int
- Returns `ParsedMonthlySummaryDocument` with rows and `HeaderDetectionWarning` flag

`MonthlySummaryValidationRules.cs`:
- Invalid month name, non-positive miles, non-positive days, days > weekdays → `ImportValidationError` list
- Intra-file duplicate months → flagged on affected rows

`IMonthlySummaryImportService.cs` / `MonthlySummaryImportService.cs`:
- `PreviewAsync(riderId, MonthlyImportPreviewRequest)` — parse → validate → expand to generated rides → duplicate check → store job + rows → return preview
- `StartAsync`, `GetStatusAsync`, `CancelAsync` — delegate to existing infrastructure (same as CSV service)
- Year assignment: months before January wrap use `StartYear`; once sequence crosses Dec→Jan, subsequent months use `StartYear + 1`

`MonthlyImportEndpoints.cs` — route group `/api/monthly-imports`:
- `POST /preview` → `PreviewAsync`
- `POST /start` → `StartAsync` (reuses `ImportStartRequest`)
- `GET /{id}/status` → `GetStatusAsync`
- `POST /{id}/cancel` → `CancelAsync`

### Phase 4 — Backend: Audit Log at Completion

**Scope**: Write `MonthlySummaryAuditLogEntity` when import job completes.

- `ImportJobProcessor` (or a new `IAuditLogWriter` service): after setting `job.Status = "completed"`, write audit log row with all FR-015 fields
- Audit log is transactional with the final `SaveChangesAsync`
- Only written for `ImportType = "monthly-summary"` jobs (guard in processor)

### Phase 5 — Frontend: New Page + Service

**Scope**: New React page for monthly import.

`monthly-import-api.ts`:
- `previewMonthlyImport(req: MonthlyImportPreviewRequest): Promise<ApiResponse<MonthlyImportPreviewResponse>>`
- `startMonthlyImport(req: ImportStartRequest): Promise<ApiResponse<ImportStartResponse>>`
- `getMonthlyImportStatus(id: number): Promise<ApiResponse<ImportStatusResponse>>`
- `cancelMonthlyImport(id: number): Promise<ApiResponse<ImportCancelResponse>>`

`MonthlyImportPage.tsx`:
- **Step 1** — File upload or paste textarea. Submit triggers preview call.
- **Step 2** — Year selector (number input). `Confirm Import` disabled until year chosen.
- **Step 3** — Preview table: generated rides per month, validation errors, duplicate flags. `HeaderDetectionWarning` banner if positional detection used.
- **Step 4** — Duplicate resolution (reuse `DuplicateResolutionDialog` component).
- **Step 5** — Progress tracking (reuse `ImportProgressPanel` component).
- **Step 6** — Summary panel (months processed, rides created, replaced, skipped, rows rejected).

Navigation entry point: add "Monthly Summary Import" link/card to existing `ImportRidesPage` or the import section.

Route: `/import/monthly` registered in `App.tsx`.

### Phase 6 — Tests (E2E Gate)

`monthly-import.spec.ts` Playwright scenarios:
1. Paste 3 months → preview shows correct ride count per month
2. Select year → dates in preview update
3. Year boundary (Nov → Feb, starting 2025) → Nov/Dec = 2025, Jan/Feb = 2026
4. Confirm import → rides appear in ride history tagged `monthly-import`
5. Re-import same month → duplicate dialog surfaces; keep-existing leaves original; replace overwrites
6. Invalid row (bad month name) → surfaced before confirmation; no rides written

## Key Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Reuse import job infrastructure | Yes — `ImportJobEntity` + `ImportRowEntity` + `ImportJobProcessor` | Monthly-generated rides become `ImportRowEntity` rows; existing processor handles them unchanged. Avoids duplicating progress tracking, cancellation, and realtime notifications. |
| New endpoint group `/api/monthly-imports` | Separate from `/api/imports` | Different input shape (monthly text vs. CSV), different preview contract. Keeps CSV and monthly import concerns isolated per SRP. |
| Weekday distribution in F# domain | Yes — `MonthlySummaryDistributor.fs` | Pure function, no I/O, composable. Consistent with existing F# domain layer housing pure calculations (savings, wind resistance). |
| Source tag via `RideEntity.ImportSource` | New nullable column | Enables filtering rides by origin without coupling to tags/notes. Future-proof for additional import sources. |
| Audit log as separate table | `MonthlySummaryAuditLogs` — write-once | FR-015 requires immutability. Separate table avoids polluting `ImportJobs` and is queryable for compliance. |
| Intra-file duplicates flagged at parse time | Backend `MonthlySummaryValidationRules` | Must block confirmation; backend is authoritative. Frontend can pre-validate for UX only. |
| Year assignment in service layer | `MonthlySummaryImportService` | Transient logic, depends on input sequence order — not a domain invariant, lives at orchestration boundary. |
